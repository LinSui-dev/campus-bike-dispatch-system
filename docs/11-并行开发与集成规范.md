# 并行开发与集成规范

## 一次性共享基线

共享远端已确定为https://github.com/LinSui-dev/campus-bike-dispatch-system.git，由用户授权建立首次main基线。正常开工直接clone并进入下一节，E核对基线和忽略规则，不重复初始化。

下面仅用于尚未建立Git的全新目录：先确认确实无仓库，不能覆盖已有仓库或把缓存提交。以下PowerShell命令在项目根目录执行：

```powershell
git init -b main
git status --short --untracked-files=all
git check-ignore .venv frontend/node_modules frontend/dist
# 人工确认只包含源码、文档、契约与课程材料，再建立基线：
git add .
git diff --cached --stat
git commit -m "chore: establish parallel development baseline"
```

若Git缺作者信息，由成员配置自己的真实身份，不编造。仅在新建且未配置origin的仓库执行：

```powershell
git remote add origin https://github.com/LinSui-dev/campus-bike-dispatch-system.git
git push -u origin main
```

以上初始化步骤仅供重建基线参考，已clone仓库不可再次执行。成员从共享main建立角色分支后即可并行，不需要等待某个业务成员先完成。

## 每人独立目录

不同电脑各自clone；同一电脑可用worktree，两者任选其一，不在同一可写目录启动多个智能体。下例为A，其他成员替换分支名为feat/b-dispatch、feat/c-frontend、feat/d-map、test/e-integration、docs/f-delivery。

```powershell
# 不同电脑：在自己选择的父目录
git clone https://github.com/LinSui-dev/campus-bike-dispatch-system.git smartTraffic-A
cd smartTraffic-A
git switch -c feat/a-engine origin/main

# 同一电脑worktree：改为在已有仓库根目录执行这一条，不再重复clone
git worktree add -b feat/a-engine ../smartTraffic-A main
```

每个目录独立.venv、node_modules和数据库，不能共享可写DB。A/B/D/E使用根.venv；C使用本目录frontend依赖；F制作材料所需工具自己准备，不改变工程依赖。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-lock.txt
npm --prefix frontend ci
python scripts/check_baseline.py
```

同机同时启动多个实例必须使用不同端口；C可在Vite代理target或本人环境配置中指定本人的后端地址，不改共享默认端口。仅做模块测试不必启动服务。

## 同步和交接

成员先提交自己的范围，不夹带他人文件，再同步公共main。下面命令在自己的工作目录执行；无远端时使用E提供的同等共享方式，不执行不存在的origin。

```powershell
git status --short
git add <自己拥有的具体文件或目录>
git commit -m "feat: describe actual module change"
git fetch origin
git merge origin/main
# 解决本人文件冲突并复验；涉及他人文件先交所有者协调
git push -u origin HEAD
git rev-parse HEAD
```

将SHA、范围和ready报告交E。E在干净集成目录按可接收模块串行合并，合并前fetch最新公共分支，合并后跑常规检查、相关真实集成与AC，填写结果再发布main。分支名和SHA应与报告一致。禁止force push公共分支，不用重写别人提交解决冲突。不规定成员整体开发顺序，只处理真实依赖。

E集成A的示例（分支名必须与实际交接对应；失败时留在集成分支修正，不推进main）：

```powershell
git fetch origin
git switch main
git merge --ff-only origin/main
git switch -c integrate/a-engine
git merge --no-ff origin/feat/a-engine
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check.ps1
# 再运行本次AC真实检查，填写接收结论并提交E拥有的证据/测试
# 确认通过后，若远端main已变化，先合入并重新验证
git fetch origin
git merge origin/main
# 复验通过后才执行下面三条
git switch main
git merge --ff-only integrate/a-engine
git push origin main
```

不要重复使用已经存在的集成分支名；后续交接改成明确的新名称。main快进失败或push被拒绝时重新同步、解决冲突和复验，不能force push。

## 契约与Mock

contracts为1.1.0基线。各成员可新增docs/integration/requests/<成员>-<主题>.md，写旧新约定、受影响方、迁移与验证。E协调受影响成员，更新版本、Schema、端口与示例，F同步文档，集成为一个兼容单元。

替身只用于独立开发。A/B可使用tests/support/doubles.py，D自己测试路网，C实现frontend/src/mocks，并用VITE_USE_MOCK=true显式开启、界面标“虚拟联调模式”。正式检查禁Mock，业务未实现HTTP明确501，不用示例掩盖失败。生产代码不得依赖tests包。

## 三层检查及迁移

|层级|命令（根目录）|含义|
|---|---|---|
|常规|powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check.ps1|契约、单元、集成基线、前端构建；不证明P0|
|骨架诊断|.\.venv\Scripts\python.exe -m pytest tests/scaffold -m scaffold|只检查当前占位阶段；不进常规门禁|
|正式验收|powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check.ps1 -Acceptance|常规后跑非空tests/acceptance，再查24项最终AC证据；空集退出5应失败|

A实现路由后不用维持501来满足骨架诊断。E将对应真实行为补入tests/acceptance并标acceptance，不能只删断言不补验收。常规health允许scaffold或implemented；API测试固定fixture profile、临时DB和独立app生命周期，E与A在应用工厂就绪后接入。正式验收要求health为implemented、无Mock，并覆盖13的必做AC。

Python 3.12、Node20为基线。A维护requirements直接依赖与requirements-lock完整锁，更新后复验；C维护package-lock，用npm ci安装。CI配置仅说明自动检查命令，未在远端执行不宣称CI通过；完整验收须E保存实际结果。

## 证据与退回

个人报告按handoffs模板，系统结果放docs/integration/results。E接受或退回交接，原所有者修自己的代码；F只引用已核实结果。测试只用临时DB，不能清理用户配置。缓存、数据库、.venv、node_modules和dist不提交，保留原始课程材料。
